# Renewal Desk · Техническое задание

**Цель.** Небольшая команда ведёт договоры с поставщиками и принимает решения о продлении до истечения срока уведомления. Renewal Desk рассчитывает этот срок по введённым условиям, показывает напоминание ответственному и сохраняет историю изменений и решений.

**Готовый сценарий.** Ответственный входит в приложение, создаёт договор с датой окончания 31 декабря 2026 года и сроком уведомления 30 календарных дней, видит дедлайн 1 декабря и напоминание с 24 ноября, фиксирует решение и видит его в истории.

## 1. Объём первой версии

- Вход и выход через сессию Rails. Создатель договора становится ответственным. Каждый пользователь видит и изменяет только свои договоры. Для демо предусмотрены два заранее созданных пользователя с разными наборами данных.
- Три основных экрана. Список с фильтрами «Открытые», «Решённые», «Все». Форма создания и редактирования. Карточка договора со сроками, напоминанием, действием для фиксации решения и историей.
- Внутренние уведомления и JSON API для списка, чтения, создания, изменения и записи решения. HTML и JSON используют одни и те же сценарии приложения и правила доступа.
- Один договор в приложении представляет один цикл продления. Запись решения о продлении или непродлении отражает внутреннее решение команды. Письма контрагенту, юридические действия, передача ответственности, загрузка файлов и новые циклы продления выходят за рамки первой версии.

## 2. Правила предметной области

| Правило | Поведение |
|---|---|
| R1. Реквизиты | При создании обязательны `title`, `counterparty`, `ends_on`, `notice_days`. Название и контрагент после обрезки пробелов содержат от 1 до 160 символов. Дата должна существовать в григорианском календаре. На границе API дата передаётся в формате `YYYY-MM-DD`, а `notice_days` — целым числом от `0` до `365` включительно. Допускается ввод уже просроченного договора. |
| R2. Дедлайн | `notice_due_on = ends_on - notice_days` в календарных днях. При `notice_days = 0` даты совпадают. Годы обеих дат лежат в диапазоне `0001`–`9999`. При разборе и арифметике Ruby использует `Date::GREGORIAN`. Время рабочих операций хранится в UTC. Для сравнения календарных дат используется дата в `Europe/Prague`. |
| R3. Состояние | Договор открыт, пока `decision` равен `null`. У открытой записи `decided_at` также равен `null`. Пока договор открыт, владелец может изменить реквизиты или зафиксировать `renew` либо `do_not_renew`. Время решения присваивает сервер. Решение допустимо и после дедлайна. После фиксации запись доступна для чтения, изменения реквизитов и второе решение отклоняются. |
| R4. Список | По умолчанию открытые договоры показываются по возрастанию `notice_due_on`, при равенстве по `id`. Тот же порядок применяется к остальным фильтрам. Просроченным считается открытый договор, если `today > notice_due_on`. В день дедлайна отображается «Срок сегодня». |
| R5. Напоминание | Открытый договор попадает в обработку, как только `notice_due_on <= today + 7`. Если на нужную дату задача была недоступна, следующий запуск обработает его, включая просроченные договоры. Напоминание создаётся один раз на версию дедлайна. |
| R6. Изменение дедлайна | `schedule_revision` начинается с `1` и увеличивается только при изменении рассчитанного дедлайна. Старое напоминание остаётся в базе для истории обработки и исчезает с карточки. При изменении реквизитов с тем же дедлайном действующее напоминание сохраняется. Решение скрывает напоминание. |
| R7. История | При создании, фактическом изменении и принятии решения пишутся `contract_created`, `contract_updated` и `decision_recorded`. Событие содержит автора и время. Изменение хранит старые и новые значения изменённых полей, решение хранит выбранный вариант. Повторная отправка актуальных реквизитов без изменений возвращает текущее состояние без нового события. |

## 3. Архитектура и модель хранения

Один Rails-монолит и один предметный контекст `Renewals`. Инкапсулируем правила договора и сроков отдельно от Rails, чтобы их можно было проверить тестами без HTTP и PostgreSQL.

| Слой | Код и ответственность |
|---|---|
| Домен | `app/domain/renewals/` содержит `Renewals::Contract` и объект-значение `Renewals::NoticeSchedule`. `NoticeSchedule` проверяет дату и период, вычисляет дедлайн и определяет, когда наступает срок напоминания. `Contract` проверяет реквизиты и допустимость переходов, управляет ревизией дедлайна. Часы передаются параметром `today` или `decided_at` из вызывающего слоя. |
| Сценарии | `app/use_cases/renewals/` содержит операции создания, изменения, записи решения и выдачи напоминания. Они загружают данные, вызывают домен и сохраняют результат в нужной транзакции. Чтение списка и карточки использует запросы Active Record с ограничением по владельцу. |
| Хранение | Active Record управляет таблицами, индексами и связями. Отдельный маппинг между `ContractRecord` и `Renewals::Contract` собирает доменную сущность через конструктор. Он же сохраняет рассчитанный доменом `notice_due_on`, чтобы сортировать и отбирать договоры по индексу. |
| Доставка | Контроллеры разбирают ввод, получают текущего пользователя, вызывают сценарий и представляют результат в HTML или JSON. Active Job запускает сценарий напоминаний. ERB отвечает за отображение. |

### Конструкторы и ошибки

- Доменная сущность создаётся со всеми обязательными данными через `initialize` с именованными параметрами. Восстановление из базы сохраняет те же инварианты. Бизнес-состояние меняется через `update_details` и `record_decision`. Публичных сеттеров у домена нет. Значения, доступные через читатели, должны быть неизменяемыми или возвращаться защитной копией. Это правило относится к доменной модели. Модели хранения используют интерфейс Active Record.
- Ожидаемые нарушения правил выражаются типизированными исключениями с предметным контекстом. Например, `InvalidNoticePeriod.new(value: 366, minimum: 0, maximum: 365)` имеет сообщение `Notice period must be between 0 and 365 days` и сохраняет параметры в `@value`, `@minimum`, `@maximum` с читателями без записи. `ContractAlreadyDecided` получает идентификатор договора и уже записанное решение. Тесты проверяют тип, `message` и доступный для чтения контекст. HTTP-граница преобразует ожидаемые ошибки в стабильные коды. Внешний ответ формируется из безопасных сообщений, а внутренний контекст остаётся доступен коду и тестам.
- Правила переходов живут в доменной модели. Транзакции и побочные эффекты управляются явно в сценариях. HTTP-коды и формат ответа определяются на границе доставки.

### Данные и конкурентные операции

| Таблица | Основные поля и гарантии |
|---|---|
| `contracts` | `owner_id`, `title`, `counterparty`, `ends_on`, `notice_days`, `notice_due_on`, `schedule_revision`, `decision`, `decided_at`, `lock_version` и стандартные timestamps. FK на пользователя. `NOT NULL` для обязательных полей. `CHECK` для допустимого периода, положительной ревизии и согласованности решения с `decided_at`. Индекс по `(owner_id, notice_due_on, id)` для списка и частичный индекс по `(notice_due_on, id)` для отбора открытых договоров. |
| `contract_events` | `contract_id`, `actor_id`, `event_type`, `payload` (`jsonb`), `created_at`. FK на договор и пользователя. Индекс по `(contract_id, id)` для чтения истории в порядке записи. Публичные операции добавляют события и читают их. |
| `reminders` | `contract_id`, `schedule_revision`, `created_at`. FK на договор и уникальный индекс по `(contract_id, schedule_revision)`. Получатель определяется по владельцу договора. |

- Изменение реквизитов и фиксация решения принимают `lock_version`, полученный при чтении. Сценарий берёт блокировку строки договора через Active Record, сравнивает версию, применяет правила и сохраняет договор с событием в одной транзакции. Устаревшая версия возвращает `409`, для HTML предлагается обновить карточку. Запись события, которая завершилась ошибкой, откатывает изменение договора. Совпавшая версия и отсутствие изменений оставляют версию и историю прежними.
- Фоновая задача запускается ежедневно в 08:00 по Праге через Active Job и Solid Queue. Она фиксирует `today` на запуск, читает кандидатов батчами и повторно проверяет состояние и срок под той же блокировкой строки. Вставка защищена уникальным индексом и пропускает конфликт по этому индексу. Повторный запуск после частичного выполнения безопасен. На карточке отображается только напоминание текущей ревизии открытого договора.

## 4. Контракты HTTP

JSON API использует префикс `/api/v1`. Тот же Rails-сеанс с cookie используется для HTML и JSON. Изменяющий запрос с активной сессией передаёт токен Rails в `X-CSRF-Token`. JSON-поля передаются в корне объекта. Идентификатор владельца берётся из сессии. Поле `lock_version` — целое число от `0`, `decided_at` сериализуется в ISO 8601 с UTC или как `null`.

| Метод и маршрут | Ввод | Успех |
|---|---|---|
| `GET /api/v1/contracts` | Необязательный `?view=open\|decided\|all`. По умолчанию `open`. | `200`, массив договоров |
| `POST /api/v1/contracts` | Все реквизиты по R1 | `201`, объект договора и `Location` карточки API |
| `GET /api/v1/contracts/:id` | Идентификатор | `200`, объект договора |
| `PATCH /api/v1/contracts/:id` | `lock_version` и хотя бы один редактируемый реквизит | `200`, объект договора |
| `POST /api/v1/contracts/:id/decision` | `decision`, `lock_version` | `200`, обновлённый объект договора |

Тело успешного ответа представляет сам ресурс или массив ресурсов. `decision` отражает решение по договору. Успех операции выражает HTTP-код. Пример ответа `GET`:

```json
{
  "id": 42,
  "title": "Office Internet",
  "counterparty": "Example Telecom",
  "ends_on": "2026-12-31",
  "notice_days": 30,
  "notice_due_on": "2026-12-01",
  "decision": null,
  "decided_at": null,
  "lock_version": 0
}
```

| Код HTTP | Когда возвращается | Примеры `code` |
|---|---|---|
| `400` | Некорректный JSON, тело не объект, неизвестное поле или неверный фильтр | `invalid_request` |
| `401` | Отсутствует активная сессия | `authentication_required` |
| `403` | У аутентифицированного изменяющего запроса отсутствует корректный CSRF-токен | `csrf_invalid` |
| `404` | Договор отсутствует или принадлежит другому пользователю | `contract_not_found` |
| `409` | Версия устарела или текущий договор уже решён | `stale_version`, `contract_already_decided` |
| `422` | Известное поле отсутствует, имеет неверный тип или значение. Сюда же относится `PATCH` без реквизитов. | `invalid_input`, `invalid_notice_period`, `invalid_date`, `invalid_decision` |

Ошибки используют `application/problem+json` по RFC 9457 с `type: "about:blank"`, стандартным `title`, числовым `status`, стабильным `code` и безопасным `detail`. При ошибке поля добавляется `field`. Сценарий изменения получает уже разобранный запрос и активную сессию. Договор загружается с ограничением по владельцу, версия проверяется под блокировкой перед доменным переходом. Повтор решения со старой версией даёт `stale_version`, с актуальной версией — `contract_already_decided`. Сериализатор не включает backtrace, SQL и сырые сообщения из неожиданных исключений. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)

## 5. Проверки для приёмки

| Уровень | Обязательные тесты |
|---|---|
| Домен, Minitest | Валидный конструктор, восстановление состояния, отклонение противоречивой пары `decision` и `decided_at`. Пустые и слишком длинные реквизиты, границы `0` и `365`, ошибки для `-1`, `366` и неверного типа. Недействительная дата, перенос на предыдущий месяц и год, високосный февраль. Ровно семь дней до срока, восемь дней, день срока и просрочка. Оба решения, решение после дедлайна, запрет редактирования и повторного решения. Ревизия при новом дедлайне и отсутствие роста при прежнем. Проверка типа, сообщения и параметров доменных ошибок. Запуск доменных тестов без Rails и базы. |
| Интеграция с PostgreSQL | Создание, изменение и решение пишут по одному событию. При ошибке записи истории транзакция откатывается. Отправка тех же реквизитов оставляет версию и историю прежними. Две конкурентные записи решения с одной исходной версией сохраняют ровно одно решение и одно событие. Повторные и параллельные запуски задачи создают одно напоминание на ревизию. Если дедлайн из списка кандидатов изменился до получения блокировки, задача учитывает новые условия. После изменения дедлайна появляется новое подходящее напоминание, старое скрыто. Для решённого договора задача не создаёт напоминание. Проверяется выбор даты по Праге на границе суток. Тесты конкуренции используют отдельные подключения и явную синхронизацию. |
| HTTP | Успешные ответы соответствуют форме ресурса и кодам из таблицы, `POST` возвращает `Location`, в успешном JSON нет поля `status`. Проверяются `400`, `401`, `403`, `404`, `409`, `422` и форма ошибки. Второй пользователь не может получить чужую запись ни через список, ни по известному ID и не может её изменить. Попытка передать `owner_id` отклоняется. Обе формы повторной фиксации решения возвращают документированные коды. |
| Браузер | Один сквозной сценарий на демо-данных проходит вход, создание, проверку дедлайна, показ напоминания после запуска задачи, запись решения и просмотр истории. Второй вход подтверждает изоляцию данных. |

Отчёт покрытия показывает строки и ветви доменного кода. Приёмка требует зелёных бизнес-сценариев из таблицы, включая ошибки и конкурентные запросы. CI запускает тесты с PostgreSQL, проверкой автозагрузки Rails и RuboCop.

## 7. M5 · AI после первой версии

Пользователь вставляет фрагмент договора и запрашивает предложения для `ends_on` и `notice_days`. Модель возвращает структурированные значения с точными цитатами из вставленного текста или `null`, если условие не найдено. Rails проверяет схему, типы, диапазоны и наличие цитат в исходном тексте. Предложения подставляются в форму после подтверждения пользователем, затем проходят обычный сценарий сохранения. Расчёт дедлайна выполняет `NoticeSchedule`.

Тесты используют заглушку провайдера и проверяют валидный ответ, отсутствие условия, неверную схему, выдуманную цитату и таймаут. При сбое доступен ручной ввод. В публичном демо используются вымышленные условия договоров.
